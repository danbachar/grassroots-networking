\section{Introduction}
\label{sec:intro}

Grassroots Networking (GN) is a peer-to-peer messaging transport that moves packets between mobile
devices over two mediums: Bluetooth Low Energy (BLE) for peers in physical proximity, and UDP over the
Internet for remote peers. The Internet relation assumes successful NAT traversal across heterogeneous
home, mobile and enterprise networks, and the decision space for that relation,
whether to dial directly with hole punching, to coordinate through a rendezvous point, or to fall
back on a relay, depends on how NAT is actually deployed in the networks our users inhabit. We have
never measured any of this: every constant in the transport, from the two-second punch to the
ten-second connection timeout, was chosen by intuition and not derived from data.

Public NAT measurements exist, but they are dated and skewed towards web and CDN workloads observed
from desktop and server vantage points~\cite{Jennings2005,Guha2005}. Mobile networks are the least
covered by those measurements, and at the same time the least favorable to traversal, as a handset
behind a carrier-grade NAT (CGNAT) cannot observe its own outer
address, cannot accept unsolicited inbound traffic, and may be assigned a different external port for
every destination it contacts, which defeats hole punching entirely. Desktop tooling cannot observe
any of this, as it does not sit behind the carrier; measuring it requires code running on handsets
carrying commercial SIMs, over the carrier networks those SIMs traverse.

In addition to the measurement gap, a second problem lies in the architecture of reachability
detection itself. The established way for a peer to learn whether it is reachable
is to ask other nodes to dial it back, as libp2p's autoNAT does~\cite{autonat}. Although autoNAT is
nominally decentralized, in practice it depends on a small set of well-known dial-back nodes, which
reintroduces the privileged infrastructure that a grassroots system is designed to do without.
GN already maintains a social graph of mutually authenticated friends, and we therefore ask whether
that graph can serve as the witness set instead, and what accuracy we lose by replacing designated
servers with friends.

In this project we design and validate a NAT detection algorithm that uses social-graph peers as
\emph{dial-back witnesses}, evaluate it against a reference implementation on a testbed under our control,
and use the resulting measurements to derive a decision rule for the transport. The results determine
whether rendezvous anchors are needed by the median user or only as a fallback, whether to invest
further in the UDP relation or push BLE harder, whether a relay is ever necessary, and how strongly to
prefer IPv6 over IPv4.

\section{The current transport and its blind spots}
\label{sec:current}

We first describe the IP path as it is implemented today, since the gaps in
Section~\ref{sec:gaps} follow directly from it. References are to files in the
\code{grassroots\_networking} repository.

The transport binds one wildcard UDP socket per address family, both on port 0, so the port is
assigned by the operating system and changes on every rebind
(\code{udp\_transport\_service.dart:1009}). A UDX multiplexer wraps each socket and owns all reads
from it. A device learns its own address in two ways: by an HTTPS request to an external reflection
service (\code{public\_address\_discovery.dart:40}), and through \code{ADDR\_REFLECT}, a signaling
message in which a well-connected peer reports the source address it observed on an incoming session
(\code{signaling\_service.dart:760}). No STUN client exists in the repository.

The address a device advertises is that discovered public IP paired with its own locally bound port
(\code{public\_address\_discovery.dart:97}), which never reveals the NAT-mapped port, and the only
source of that port requires a session which already works. Self-classification is a single boolean,
\code{isWellConnected}, computed as a routability test over the advertised string; the test correctly
excludes 100.64/10 among other reserved ranges (\code{address\_utils.dart:138}), but a handset behind
a CGNAT never observes its inner address, so the exclusion never applies to it.

Peers advertise address candidates in a signed \code{ANNOUNCE} that repeats every ten seconds; the
same timer drives liveness, reconnection and the queued-message drain, and there is no dedicated NAT
keepalive. Candidate selection scans every local-remote pair and returns exactly one, ranked
link-local, then IPv6, then IPv4 (\code{connection\_service.dart:48}); nothing probes candidates in
parallel, validates them, or falls back to the second-best pair after a failed attempt. The hole punch
is a 36-byte packet carrying a magic value and the sender's public key, sent for two seconds at
200\,ms intervals to a single address and port, without port prediction
(\code{hole\_punch\_service.dart:117}). A closed-loop variant exists but has no production caller and
cannot function as wired, since it reads the raw socket that the multiplexer already owns. The dial
itself is a single UDX attempt with a ten-second timeout and no retry inside the transport.

\subsection{What we cannot currently determine}
\label{sec:gaps}

\textbf{No NAT classification}: no code determines mapping or filtering behavior, and the boolean
standing in for it is systematically wrong for handsets behind a CGNAT, which advertise a globally
routable address and are therefore classified as well-connected by themselves and by their peers.
Three behaviors follow: the pre-connect punch is suppressed for peers that appear public
(\code{grassroots\_network.dart:3369}) and is thus skipped for the peers that require it; the device
begins acting as an address reflector and rendezvous facilitator; and the interface reports the device
as well-connected. Nothing distinguishes having a public address from being reachable at it.

\textbf{No mapped-port discovery}: the port we instruct peers to dial is a guess whenever no session
has yet succeeded, which is the case that matters for a first contact.

\textbf{No use of reflector disagreement}: several rendezvous servers and well-connected friends may
each reflect the same socket, which is precisely the raw material of an RFC 5780 mapping test, but the
handler overwrites the stored address and retains nothing, so two disagreeing reflections are
indistinguishable from a roaming event.

\textbf{No dial-back and no witnesses}: reachability from outside is asserted from an address prefix
and never tested, and the inbound-connection observation point that exists in the transport is never
read for a decision.

\textbf{No instrumentation}: punch outcomes are a four-value enumeration without timestamps and the
reducer discards the failure reason, so neither latency nor robustness can be computed after the fact.
Punching being open-loop, a refused mapping, a lost packet, a wrong port and a slow handshake are
indistinguishable in the logs.

These combine in practice. Consider two friends previously paired over BLE and now remote: one behind
a carrier CGNAT on an IPv4-only path, the other behind a consumer router with IPv4 and a working IPv6
prefix. The first advertises the carrier's outer address with its own local port, and both compute
that it is well-connected, which is wrong in the port and in the reachability it implies. Candidate
selection then prefers the second device's IPv6 address, as an IPv6 socket is bound on the first even
though it has no IPv6 transit, and the single attempt times out after ten seconds without falling back
to IPv4. The punch is suppressed on both sides, each observing the other as public, and had it fired
it would have targeted the local ports. Nothing is recorded, and the failure is indistinguishable from
the peer being offline; on a port-preserving NAT, where the guessed port is correct and the attempt
succeeds, nothing is learned either.

\section{Research questions}
\label{sec:rqs}

\textbf{RQ1}: can social-graph peers replace designated dial-back servers? We specify a witness-based
algorithm that recovers a peer's mapping and filtering behavior, and quantify its agreement with an
RFC 5780 reference implementation.

\textbf{RQ2}: what does decentralization cost? Under the honesty assumption of
Section~\ref{sec:assumption} the cost is statistical and not adversarial, and takes three forms. How
many witnesses does a confident verdict require? The minimum set is fixed by the test matrix of
Section~\ref{sec:algorithm} rather than by any accuracy target, so the open question is how many
repetitions and how many further friends are needed for confidence, given that a dial-back may fail to
arrive for reasons unrelated to our NAT. What does disagreement between witnesses at different vantage points indicate,
since under honest peers it is diagnostic rather than malicious? And what is the availability
constraint, $P(\geq k$ friends online at an uncontacted vantage point$)$, which we expect to dominate
in practice?

\textbf{RQ3}: which NAT behaviors occur in the networks our users inhabit, and how prevalent are
they? We measure the tuple of Section~\ref{sec:measurand} per stratum on our own devices, and estimate
population prevalence by weighting strata with published subscriber counts, as described in
Section~\ref{sec:prevalence}.

\textbf{RQ4}: what should the transport do at dial time? We derive a decision rule over the inputs
the transport holds at the moment it must decide, namely to attempt directly, to request mediation,
or to abort, and validate it by replay.

\subsection{Measurand}
\label{sec:measurand}

Instead of a NAT type, and following RFC 4787 and RFC 5780~\cite{rfc4787,rfc5780}, we decided to
measure a tuple: \emph{mapping behavior}, which is endpoint-independent, address-dependent or
address-and-port-dependent; \emph{filtering behavior}, which is endpoint-independent (EIF),
address-dependent (ADF) or address-and-port-dependent (APDF); \emph{port preservation}; and
\emph{mapping lifetime}.
The orthogonal facts of CGNAT suspicion and IPv6 availability are recorded alongside. A single-label
NAT type may be derived from the tuple for presentation, but is never the measurand.

The tuple is measured and reported per address family and per translation path, which is either NAT44,
NAT64 with 464XLAT, or native IPv6. On a 464XLAT path the entity being characterized is the carrier's
translator, which the RFC 4787 vocabulary describes only partially, and on a native IPv6 path there is
typically no mapping at all and only stateful filtering, so mapping behavior and port preservation
are reported as not applicable rather than as absent. The translation path therefore splits strata and
is not an orthogonal attribute.

We note that autoNAT does not produce this measurand. Version 1 reports whether a node is publicly
reachable, and version 2 reports whether a given address is dialable, with a nonce in the dial-back
request~\cite{autonat}; neither emits a mapping or filtering label. The categorization is therefore
ours to implement and not to import: the dial-back idea is taken from autoNAT, but the classifier that
turns a set of dial-back outcomes into a mapping and filtering label is part of the delivered code.
Ground truth for it is an RFC 5780 reference server that we operate ourselves.

\section{Approach}
\label{sec:approach}

\subsection{Witness-based detection}

To characterize the path the transport actually uses, we decided to implement the probe inside
\code{grassroots\_networking}, under \code{lib/src/transport/}, and to send from the transport's
existing per-family socket instead of from a socket of its own, as a second socket receives a
different NAT mapping and thus characterizes a different path altogether. The UDX fork exposes a
raw-packet callback for this purpose, and three properties of the existing code constrain its use: the
raw handler discards datagrams shorter than 50 bytes and 36-byte punch packets, so probes must exceed
50 bytes and carry their own magic value; the existing raw send path registers targets in a map that
is not cleared on shutdown, so a separate send path is required to keep the announce broadcast away
from measurement targets; and the closed-loop punch mode is inoperative for the read-ownership reason
given in Section~\ref{sec:current}.

Several components are reused instead of rebuilt: the punch service, the address-class labeler in
\code{address\_utils.dart}, which already excludes CGNAT, ULA, Teredo and 6to4, the candidate scorer
on which the probe loop is layered, the Noise session manager for the authenticated channel, the
signed invite records as the template for a witness attestation, and \code{bootstrap\_anchor/}, which
runs without Flutter and is therefore the natural host for the reference server.

Every witness is a friend of the probe, and the probe addresses each of them directly. We considered
having one friend relay a dial-back request onwards to a further node, and rejected it: signaling in
GN is friend-only by design, so that a device never acts on behalf of an arbitrary peer, and a request
that causes a packet to be sent to a third party is precisely the amplification vector autoNAT v1
refused to create. Restricting witnesses to friends removes that vector by construction, and the
requests travel on the existing signaling plane inside Noise sessions, where clear signaling is
refused on both ends and the eleven types in use occupy \code{0x05}--\code{0x0f}, so that the witness
messages are purely additive from \code{0x10} upwards.

Each friend performs two functions. It \emph{reflects}, by reporting the source address and port it
observed for the request, and it \emph{dials back} on request, sending the probe a packet carrying the
client-chosen nonce from a source it names in its reply. The nonce is what makes the report
unforgeable: a friend cannot claim a dial-back that never arrived, since the probe accepts only a
packet carrying the value it generated.

Mapping behavior follows from the reflections. Two friends at distinct addresses, plus one reporting
from a second local port, establish whether the mapped port varies with the destination.
\code{ADDR\_REFLECT} already performs the reflection; what remains is to solicit it from a second
distinct address and to retain each observation as a \code{(reflector, tuple, timestamp)} triple
instead of overwriting it.

The provenance is worth stating, as it is easily misread. The measurand and the test procedures come
from RFC 4787 and RFC 5780; the dial-back mechanism comes from autoNAT, which is a libp2p protocol
specification and not an RFC; and the substitution of friends for designated servers is ours. What the
student implements is therefore the RFC 5780 procedures with friends supplying the alternate vantage
points that the RFC expects a dual-homed server to supply.

Filtering behavior follows from where the dial-backs originate, classified against the probe's own
send history rather than against the identity of the friend. A dial-back from an address and port the
probe currently has a session with establishes the baseline; one from the same address on a fresh
source port separates address-and-port-dependent filtering from the rest; and one from an address the
probe has never transmitted to separates address-dependent from endpoint-independent filtering. The
third arm is the constraining one, as it requires a friend with which no session is currently open, or
a second address of a multi-homed friend that the probe has not used. Friends with a stable public
address are the most valuable witnesses for it, and the number of distinct uncontacted vantage points
the friend set can present bounds which filtering classes are separable at all.

\subsection{The procedure}
\label{sec:algorithm}

A run proceeds in two rounds over a chosen set of friends, each of which is recorded with its address,
its port, and whether the probe has previously transmitted to it.

\emph{Round one, reflection.} Each friend reports the source address and port it observed. Writing
$R(f)$ for the tuple reported by friend $f$, the mapping label follows from how $R$ varies:

\begin{longtable}{L{7.4cm} L{7.4cm}}
\toprule
\rowcolor{headerblue}
\textcolor{white}{\textbf{Observation}} & \textcolor{white}{\textbf{Mapping label}} \\
\midrule
\endhead
$R$ identical for every friend & endpoint-independent \\
\rowcolor{rowgray}
$R$ differs across friends at distinct addresses, but agrees across two ports of one friend &
address-dependent \\
$R$ differs across two ports of the same friend & address-and-port-dependent \\
\bottomrule
\end{longtable}

\emph{Round two, dial-back.} The probe requests three dial-backs, each carrying the nonce, and
classifies filtering by which of them arrive. $D_1$ originates from an address and port the probe has
transmitted to, $D_2$ from that same address on a source port it has not, and $D_3$ from an address it
has never transmitted to.

\begin{longtable}{L{7.4cm} L{7.4cm}}
\toprule
\rowcolor{headerblue}
\textcolor{white}{\textbf{Arrivals}} & \textcolor{white}{\textbf{Filtering label}} \\
\midrule
\endhead
$D_3$ arrives & endpoint-independent \\
\rowcolor{rowgray}
$D_3$ absent, $D_2$ arrives & address-dependent \\
$D_2$ absent, $D_1$ arrives & address-and-port-dependent \\
\rowcolor{rowgray}
$D_1$ absent & inconclusive: retry, then report no path \\
\bottomrule
\end{longtable}

An arrival is definitive and terminates its arm. An absence is retried under the policy of
Section~\ref{sec:aggregation} before it is recorded, since under honest peers an absent dial-back is
equally consistent with filtering and with loss.

\emph{How many friends this needs.} The answer is combinatorial before it is statistical. Separating
endpoint-independent from address-dependent mapping requires two friends at distinct addresses;
separating address-dependent from address-and-port-dependent requires one friend reachable on two
ports; the endpoint-independent filtering test requires one friend never transmitted to; and the
remaining filtering distinction requires a contacted friend able to send from a fresh source port.
Three friends with the right properties therefore suffice to make every class separable, and no number
of additional friends improves the resolution. What further friends and repetitions buy is confidence
against loss, which is the subject of Section~\ref{sec:aggregation} and of the second experiment.

\subsection{Contamination}
\label{sec:contamination}

The central validity threat, which we call \emph{contamination}, is that social witnesses are by
construction the peers the device already transmits to, through an \code{ANNOUNCE} every ten seconds
on every live connection and roughly ten punch datagrams per traversal attempt. A dial-back from an
endpoint the probe has previously contacted traverses a mapping the probe itself opened, and therefore
measures the probe's own behavior instead of the NAT's filtering rule, biasing results towards
permissiveness.

We mitigate this with a per-test send history of every destination emitted on the measured socket: a
witness source appearing in that history is a logged discard condition, and the strict filtering arm
must originate from an endpoint never contacted. This constrains witness selection rather than the
protocol, as the friends currently in session are precisely the contaminated ones, and it makes the
availability question sharper: what matters is not how many friends are online, but how many are
online at a vantage point the probe has not already used. Running the same test with and without
a prior punch towards the witness quantifies the bias that naive witness-based tests incur.

\subsection{Assumption: honest peers}
\label{sec:assumption}

We assume throughout that peers are honest: a friend that reports a dial-back performed it, and a
friend that reports a failure observed one. This is a stated assumption and not a claim about the
deployment, and relaxing it --- witnesses that fabricate successes, withhold them, or collude --- is a
natural extension of this work and not part of it. Two consequences are worth separating, as only one
of them disappears under the assumption.

What disappears is the need to defend against a lying witness, and with it the byzantine analysis. No
quorum is required to establish that a dial-back happened, and a reported failure can be taken at face
value as that witness's own observation.

What remains is that the network is not honest merely because the peers are. An off-path party can
still inject a packet resembling a dial-back, and the probe would otherwise conclude that it is
reachable when it is not. The client-chosen nonce therefore stays, with a different justification: it
binds an arriving packet to the request that solicited it, distinguishing a genuine dial-back both
from unrelated traffic and from injection by a party that is not a friend.

\subsection{Aggregation and failure semantics}
\label{sec:aggregation}

Success and failure are not symmetric, and under honest peers the asymmetry follows from packet loss
and not from deceit. A dial-back that arrives carrying the nonce is definitive: the path exists and
the NAT admitted it. A dial-back that does not arrive is not definitive, as it is equally consistent
with the NAT filtering the packet, with the witness being unable to send from the requested source,
and with ordinary loss on either path.

The aggregation rule follows. Any verified arrival establishes the property under test. An absence is
recorded as inconclusive until the arm has been retried and attempted through $k$ independent
witnesses, and only then reported as a negative result. The retry and timeout policy is therefore part
of the specification and not an implementation detail, and the residual probability that a genuinely
open path is reported closed is a quantity the evaluation must state.

Disagreement between witnesses is a measurement signal under this model and not a sign of misbehavior.
Where one vantage point succeeds and another fails, the likely explanation is that the behavior under
test genuinely depends on the source address or port, which is precisely the distinction between
endpoint-independent, address-dependent and address-and-port-dependent filtering. Disagreement is
therefore retained and classified, never voted away.

Two engineering constraints survive the assumption, as they protect parties outside it. A dial-back
targets only the source address the friend itself observed, and never an address carried in the
request, so the protocol cannot direct traffic at a third party; this is what the friends-only
restriction of Section~\ref{sec:approach} buys. And the probe refuses to dial or punch any target that
is not globally routable, using the predicate already present in \code{address\_utils.dart} but not
applied on the punch path. Measurement traffic from the probe is confined to the testbed by a target
allowlist enforced at the send path, and measurement is never enabled in the production build. The one
exception is the external cross-check of Section~\ref{sec:crosscheck}, which is run deliberately and
by hand, from a separate process rather than from the probe.

\subsection{An external cross-check}
\label{sec:crosscheck}

The classifier consumes dial-backs from friends only. Separately, and clearly labeled as such, we
query the public libp2p autoNAT nodes as an outside reference on \emph{reachability alone}, so that
our friends-only verdict is not the only opinion in the record. Three caveats determine how much this
can be asked to carry.

It answers a narrower question. autoNAT reports whether a node is publicly reachable, and version 2
whether a given address is dialable; neither yields a mapping or filtering label, so the cross-check
can corroborate or contradict a reachability verdict and nothing more.

It measures a different socket. Speaking to those nodes requires a libp2p host, and embedding one in
the application is the cost this project explicitly avoids, so the cross-check runs as a small
standalone client on a general-purpose host attached to the same network. It therefore characterizes
the \emph{network} rather than the transport's own socket, and on cellular it can only be run by
tethering, which inserts a further translation layer and makes the comparison invalid. We run it on
Wi-Fi networks and state the cellular gap rather than papering over it.

It leaves the testbed. The requests go to public infrastructure that exists to answer them, they are
protocol-conformant and few, and they are issued by hand rather than by the probe. This is the only
measurement traffic in the project that is not confined to hardware we control, and it is recorded as
such.

\subsection{Prevalence estimation}
\label{sec:prevalence}

A convenience sample of our own handsets cannot be averaged into a prevalence figure directly, but it
need not be, as NAT behavior is primarily a property of the network path and not of the individual
subscriber: every customer of one carrier, on the same access point name (APN) and PDN type,
traverses the same small set of gateway configurations. We therefore characterize each \emph{stratum}
on the testbed and weight the strata by published population data, accepting that with few
measurements per stratum the within-stratum variance is not estimable and can only be bounded by
assumption. This is a stratified census of strata and not a stratified sample, as there is no
probabilistic sampling within a stratum; no confidence interval is therefore computable, and every
interval we report is a sensitivity range over assumptions. One subscriber-level determinant survives
this argument: the handset stack selects the PDN type and whether a translator is present, and since
Android and iOS differ here, each cellular stratum is measured on at least two handset stacks, one of
each platform.

\textbf{Cellular strata}: one per carrier, APN and PDN type, and not one per carrier. These strata
are few and cheap to enumerate, but each carries a large weight, which is why an undetected error
inside one is expensive and why each is covered by at least two SIMs and two handset stacks before its
homogeneity is treated as established. Homogeneity within a carrier remains an assumption, and the
ways it fails are known: the APN tier, as a consumer prepaid SIM generally cannot reach corporate or
M2M gateways; the operator arrangement, as a full MVNO runs its own core and NAT and is a separate
stratum while a light MVNO is not; the regional gateway pool; and the behavior of the address pool
under exhaustion.

\textbf{Residential strata}: one per ISP and per whether that ISP applies CGNAT to the subscriber,
with customer-premises equipment vendor and firmware family as a secondary split within the
non-CGNAT cells only. The ordering matters, as CGNAT above the customer equipment renders that
equipment unobservable from outside, and as ISP subscriber share is published whereas equipment share
by firmware family is not. These strata are the weak half, since the number of models, the drift of
firmware and subscriber-configurable settings make homogeneity within the secondary split a genuine
assumption; should its weights prove unobtainable, we report residential results as an interval across
the observed cells, weighting only the ISP and CGNAT axis.

\textbf{Managed and public networks}: university, office and commercial hotspots, characterized as a
set and carried with a coarse and explicitly uncertain weight.

\textbf{Residual stratum}: tethered clients, whose NAT stacks above the carrier's; VPN and
private-relay users, who replace the measured path entirely and are over-represented in the
privacy-conscious population GN attracts; fixed-wireless and satellite broadband, residential in name
but cellular in mechanism; and enterprise networks. We do not measure it, and carry it at its best
available weight so that it enters the bound at both extremes and the weight table sums to the
denominator.

The denominator is consumer-APN mobile lines and residential broadband lines in the countries we
cover, at the date of measurement, and not devices, humans or GN users. Published subscriber counts
include machine-to-machine and data-only lines, which we net out where the source permits and flag
where it does not, and they are cross-checked against per-AS end-user estimates such as APNIC's, which
sample eyeball users per AS and cannot separate cellular from fixed for a carrier announcing both
under one ASN. Weights are never taken from the announced address space, which is uncorrelated with
user population once CGNAT is present.

We report prevalence with its weight table and a sensitivity analysis in four arms: under each
independent published weighting; under a worst-case and best-case assignment of all unmeasured and
heterogeneity-uncertain mass to the extremes of the measurand domain, which is the only arm that
bounds the conclusion; under the assumption that unmeasured strata behave as the worst observed one,
which is a pessimistic variant and not a bound; and under perturbation of each measured stratum's
label across the range its homogeneity check observed. We name the dominant envelope and report the
cellular and residential halves separately. Comparison against published NAT
and DCUtR measurements~\cite{dcutr} is performed only where the denominators reconcile, as those
studies estimate over libp2p nodes and traversal attempts and are skewed towards always-on desktop and
datacenter hosts.

\section{Experiments}
\label{sec:experiments}

The evaluation is conducted entirely on a testbed under our control, in two tiers. The first tier is a
synthetic bench whose labels are known by construction, and on which the correctness claim is
established. The second tier consists of our own handsets, carrying prepaid SIMs across the local
carriers, moved across the access networks we can physically reach. As the second tier carries no
labels, we report agreement with the reference implementation rather than accuracy, and treat
disagreements as a category with hypotheses such as mapping churn during a test, rate limiting at the
reference server, or multipath.

\subsection{Bench validation against a reference implementation}

\paragraph{Question.} Does the witness-based algorithm recover the mapping and filtering behavior of
a NAT whose configuration is known by construction, and how does its agreement compare with that of an
RFC 5780 reference server?

\paragraph{Setup.} A reference server with two public addresses and two ports per family, verified to
advertise its alternate address and to honour change requests from it. Netfilter spans two of the
three mapping classes: the default masquerade rule reuses a mapping per source tuple and presents as
endpoint-independent, while \code{--random-fully} allocates a fresh port per flow and presents as
address-and-port-dependent. No option produces address-dependent mapping, which is therefore
constructed with per-destination source NAT through nftables maps; \code{--persistent} controls the
source address pool and is not on this axis. The bench additionally spans EIF, ADF and APDF filtering,
two to three commercial routers, and a double-NAT configuration emulating CGNAT.

\paragraph{Procedure.} Each configuration is measured by the reference server and by the
witness-based algorithm with three honest witnesses, back to back within one window. The
contamination guard is then disabled and the filtering arm repeated with a punch issued towards the
witness beforehand, to quantify the bias it prevents.

\paragraph{Measures.} Per-configuration labels from each method against the construction label;
wall-clock time to verdict; bytes transmitted and received per verdict.

\paragraph{Output.} Confusion matrices against the construction labels for at least eight
configurations; agreement of the witness-based algorithm with the reference server; and the label
difference between contaminated and uncontaminated runs.

\subsection{Witness count and failure semantics}

\paragraph{Question.} How many honest witnesses does a confident verdict require, how much of an
apparent negative is ordinary loss, and does disagreement between vantage points correspond to genuine
address- or port-dependence?

\paragraph{Setup.} Witness processes on the bench, at distinct addresses and ports, against
configurations whose filtering behavior is known by construction. Loss is injected on the return path
at controlled rates.

\paragraph{Procedure.} Sweep the witness count $k$ and the retry policy against injected loss. For each
configuration, record whether the verdict is correct, inconclusive or wrong, and compare the pattern of
witness disagreement against the configuration's known dependence on source address and port.

\paragraph{Measures.} Rate of wrong and of inconclusive verdicts per $(k,$ retry policy, loss rate$)$;
time to verdict; number of dial-back requests per verdict; agreement between vantage points.

\paragraph{Output.} Wrong-verdict and inconclusive rates against $k$ for each loss rate, giving the
witness count and retry policy at which a verdict becomes trustworthy; the residual probability that an
open path is reported closed; and a mapping from disagreement patterns onto the filtering classes they
indicate.

\subsection{Testbed campaign across strata}

\paragraph{Question.} Which values of the measurand occur across the strata of
Section~\ref{sec:prevalence}, and how stable is each stratum under repetition and under variation of
the subscriber configuration?

\paragraph{Setup.} The handsets and SIMs of the testbed inventory. Each cellular stratum is covered by
at least two SIMs differing in plan or operator arrangement, and by at least two handset stacks.

\paragraph{Procedure.} Each stratum is measured on at least two days, spanning a peak and an off-peak
window, with the screen on and off and the application in the foreground and the background. Roaming
and handover are triggered deliberately. Mapping lifetime is probed per network with the announce
timer quiesced for the duration of the probe.

\paragraph{Measures.} The full measurand per stratum, with the translation path; the pairwise
agreement between the subscriber configurations within a stratum, which serves as the homogeneity
check; interface type, radio technology, screen state and application state per record; and agreement
with the reference server.

\paragraph{Output.} A per-stratum table of the measurand; the homogeneity check per cellular stratum,
where a disagreement splits the stratum rather than being averaged; the list of strata that were not
reached, with their population weight, so that the coverage gap is quantified; and the weighted
prevalence estimate with the four-arm sensitivity analysis of Section~\ref{sec:prevalence}.

\section{Deliverables}
\label{sec:deliverables}

\begin{itemize}
  \item The detection algorithm: a specification with its stated assumptions and failure semantics, a
        reference implementation
        in \code{grassroots\_networking}, and its validation against the RFC 5780 implementation.
  \item The classifier itself, as delivered code: the rule that turns a set of dial-back outcomes,
        each from a friend at a known vantage point, into a mapping and filtering label together with
        the confidence in it. A specification-level comparison against autoNAT states what each
        protocol reports and its cost in bytes and round trips per verdict, and a spot cross-check
        against public autoNAT nodes corroborates the reachability verdict on Wi-Fi networks.
  \item The testbed dataset: every bench configuration with its construction label and every stratum
        with its measured tuple, released in full, as these are our own devices on our own SIMs. We
        check the acceptable-use terms of each plan beforehand, as consumer terms occasionally
        prohibit network probing.
  \item Prevalence estimates with the weight table, the denominator, the date of measurement and the
        sensitivity analysis, cellular reported separately from residential.
  \item A per-attempt instrumentation subsystem recording the attempt identifier, peer, candidate,
        address family, path taken, phase timestamps, outcome and failure kind, with a durable sink;
        the identifier travels on the control messages so that both endpoints' records join.
  \item A decision rule for the transport, validated by replay on a held-out split.
  \item A technical report, targeting ANRW or PAM.
\end{itemize}

The primary claim is the detection algorithm, validated on labeled ground truth and exercised against
real access networks; the prevalence estimate, the reachability comparison and the decision rule are
supporting results, and broadening the testbed to further carriers is pursued if time permits. Related
work is written in the first month and not the last, as a longitudinal DCUtR campaign already covers a
large number of traversal attempts~\cite{dcutr}, against which our defensible axes, namely cellular
carriers and CGNAT observed from real handsets and the decentralization of the witness set, must be
positioned from the outset.

\subsection{Hosting the fixed infrastructure}
\label{sec:hosting}

Three components sit outside the handsets, and a university network is a good candidate for all three,
provided one requirement is met.

The \textbf{oracle} needs two globally routable addresses per family, each reachable on two UDP ports,
and it must be able to receive unsolicited inbound datagrams on them. This is the requirement that
decides everything else, as a border firewall that drops unsolicited inbound UDP makes the host
unusable however many addresses it has. It is worth establishing in week~1 whether such an exception
can be obtained, and for which ports, because the alternative is a commercial virtual machine with a
second address purchased.

The \textbf{witnesses} need distinct vantage points rather than capacity. Instances on separate
subnets give the distinct-address arm of Section~\ref{sec:algorithm}, and a second listening port on
one of them gives the port arm, so a handful of small hosts on different segments is more valuable
than one large host.

The \textbf{bench} can be hosted rather than assembled on a desk. Running the netfilter configurations
inside network namespaces on a single always-on machine makes the topologies reproducible from a
script, allows nested translation to be built for a double-NAT case, and removes the physical routers
from the labeled tier, where Section~\ref{sec:experiments} notes they never belonged, since their
policy is observed rather than known by construction.

Mininet is a reasonable way to drive those namespaces, and we expect it to be used, but it should be
adopted for what it actually provides. It supplies the plumbing: hosts as namespaces, links as veth
pairs, the topology expressed as a Python script, and per-link loss and delay through \code{TCLink},
which is what the loss injection of Section~\ref{sec:experiments} needs. It does not supply the NAT
classes. Its built-in NAT node is a plain masquerade, so each class in Section~\ref{sec:measurand}
still has to be written by hand in netfilter or nftables, and the address-dependent case still has no
native expression. Plain \code{ip netns} with a set of rule scripts would serve equally well; the
choice is one of convenience, and it should be recorded as such rather than presented as the source of
the labels.

Two further points govern how far the emulation can be trusted. First, an emulated NAT is only the
outermost translation if the host carrying it is itself untranslated: if the machine sits behind a
campus or home NAT, a remote peer observes the composition of that NAT with ours, and the label we
constructed is not the label the peer sees. A publicly addressed host is therefore a precondition for
any run in which the counterpart is outside the emulation, which is the same requirement the oracle
imposes. Second, and consequently, the labeled tier is cleanest when the counterparts live inside the
emulation as well: witnesses at distinct emulated addresses and a two-address oracle are trivial to
provision as further namespaces, and the whole run stays on one machine with nothing traversing a
network we do not control. Dialing a node outside the emulation belongs to the cross-check of
Section~\ref{sec:crosscheck}, where the composition caveat is stated rather than assumed away.

What the emulation cannot supply is the behavior of a real carrier: pool exhaustion under load, the
differences between one operator's APNs, and the quirks of a particular gateway generation are outside
its reach. It reproduces a \emph{class}, not a network, which is why the field tier remains the
handsets.

One caveat is worth stating plainly, as it inverts the usual intuition. A campus network is an
excellent place to stand \emph{outside} a NAT and a poor subject to measure, since university
allocations are typically large enough that wired hosts are publicly addressed and not translated at
all. The subjects of the measurement remain the handsets on carrier and residential paths; what the
institution supplies is the vantage points they are measured against. Campus wireless, the guest
network and the institutional VPN are separate matters, as each is a genuine access network with its
own policy and each is worth characterizing in its own right.

\subsection{What this deliberately excludes}

Three items that belong to the research question are outside a semester and are named here so that
their absence is a decision and not an oversight. The \textbf{autoNAT sidecar} is removed, as
embedding the reference implementation in the application is a project of its own; the protocol
comparison is specification-level, and the external corroboration is the standalone spot cross-check
of Section~\ref{sec:crosscheck} and not an in-app baseline. The \textbf{prevalence estimate} and its weighting and sensitivity
analysis are follow-on work; this semester produces the per-stratum measurements it would consume.
And the \textbf{decision rule} for the transport is left to that follow-on, as fitting it needs more
networks than a semester will reach.

\subsection{What counts as success}

The project succeeds if the work is done properly and reported honestly, and not if a particular
number comes out. Concretely: the probe is implemented and sends from the transport's own socket, or
the reason it cannot is documented; the bench is reproducible and its labels are known by
construction; the witness algorithm's agreement with the oracle is measured and every disagreement is
explained; the contamination guard's effect is quantified; and the limitations are stated. A result in
which the witness approach agrees poorly with the oracle is a finding, and is written up as one --- it
would tell us that friends are not a sufficient substitute for designated servers, which is precisely
what the project set out to determine.

Excellent work is distinguished by what it adds beyond that: a characterization of \emph{why} the
disagreements occur, a retry and timeout policy derived from measured loss rather than assumed, or
coverage of a carrier whose behavior was not anticipated.

\section{Prerequisites and open decisions}

We expect basic mobile application development, basic networking, and familiarity with statistics and
a plotting library; experience with a peer-to-peer stack is an advantage. Dart is learned in the first
weeks, and the onboarding checkpoint exists to make that concrete rather than assumed. The student
needs a Linux host for the bench, two publicly routable addresses for the oracle, at least one Android
and one iOS handset, and any SIMs the measurement is to cover.

Five decisions are taken before the work begins. First, ownership of the UDX fork: the send history
behind the contamination guard cannot see UDX's own retransmissions and keepalives, as the fork
exposes a receive hook but no general send hook, so either the student is given a path override and
the right to publish a patched fork, or the guard is defined over the sends the application controls
and the residual is reported as a limitation. Second, whether the probe shares the transport socket,
which the week-3 checkpoint answers, and what is reported if it cannot. Third, who hosts the fixed infrastructure. It has
three roles and one hard requirement, set out in Section~\ref{sec:hosting}. Fourth, whether to open an IPv4 rule on the deployed rendezvous
anchor, whose data-plane rule today admits \code{udp:9516} from \code{::/0} and is therefore IPv6
only, which excludes the IPv4-only CGNAT population the study targets. Fifth, the measurement budget:
each carrier is a candidate stratum, but each SIM covers only one combination of carrier, APN and
plan.

We note separately that the unvalidated punch target, the absence of rate limiting on the signaling
path, the uncorroborated address reflection and the unbounded length field in the stream framer are
defects in the current implementation, independent of this project, and that their assignment should
be settled in advance.

\section*{Glossary}

\begin{description}[leftmargin=0pt, style=nextline, itemsep=0.2em]
  \item[464XLAT] A mechanism allowing IPv4-only applications to operate over an IPv6-only mobile network, by
        translating on the handset and again in the carrier network. Android and iOS differ in their
        support, so the handset stack can change what a measurement observes.
  \item[APN] The named gateway configuration a mobile device uses to reach the packet core. Prepaid,
        postpaid, corporate and machine-to-machine plans frequently use different ones, and therefore
        potentially different NAT behavior on the same carrier.
  \item[autoNAT] A libp2p service in which a node asks other nodes to dial it back to determine whether it is
        publicly reachable, per address and with a nonce in version 2. Both versions rely in practice
        on well-known dial-back servers, and neither classifies NAT behavior.
  \item[CGNAT] Network address translation applied by an ISP, typically a mobile carrier, sharing one public
        IPv4 address among many subscribers, so that even the public address is shared.
  \item[Dial-back] A request from peer A that peer B attempt a connection back to A, whose success establishes
        that A is reachable from outside.
  \item[Filtering behavior] Which inbound traffic a NAT admits on an existing mapping: endpoint-independent,
        address-dependent, or address-and-port-dependent. Determining it requires a packet from an
        endpoint never contacted.
  \item[Hole punching] Two peers behind NATs transmit towards each other simultaneously, so that each NAT admits
        the reply to traffic it has already seen. It generally fails against address-and-port-dependent
        mapping.
  \item[Mapping behavior] How a NAT allocates the external port for outbound traffic: the same port for every
        destination, or a fresh one per destination, in which case no peer can predict where to send.
  \item[Mapping lifetime] How long a NAT retains an idle mapping, which determines the keepalive interval required
        to hold a path open.
  \item[MVNO] An operator reselling service on another operator's network. A full MVNO runs its own packet
        core and NAT and is a separate stratum; a light MVNO is not.
  \item[Port preservation] Whether a NAT retains the internal source port as the external one, in which case the
        address a device guesses from its own local port is correct.
  \item[RFC 4787, RFC 5780] The former defines NAT behavioral terminology and requirements, the latter the tests
        that discover that behavior from outside, using a server with two addresses and two ports.
  \item[STUN] A protocol by which a peer asks a public server which address it appears to originate from. GN
        has no STUN client, and \code{ADDR\_REFLECT} is its nearest equivalent.
  \item[UDX] The reliable multiplexed stream protocol over UDP used for the Internet relation, consumed as
        a fork published as \code{grassroots\_dart\_udx}.
\end{description}
